5. Di mana staging hidup?

Koneksi A · pipeline PythonBEGIN → buat staging → isi staging → merge sales
Seluruh operasi memakai objek conn yang sama
COMMITPerubahan sales tersimpan.
Staging dihapus oleh ON COMMIT DROP.
ROLLBACKPerubahan sales dibatalkan.
Pembuatan staging juga dibatalkan.

Koneksi B, misalnya SQL editor, tidak bisa melihat tabel sementara milik koneksi A. Menjalankan merge_sales.sql sendirian biasanya gagal karena staging belum dibuat pada sesi editor tersebut.

Tabel sementara berada di schema sesi PostgreSQL, misalnya pg_temp_3. Namanya bisa berbeda. Staging dibuat dengan nama dan tipe kolom hasil SELECT, tanpa data; bukan salinan lengkap constraint atau indeks tabel utama.

Untuk pipeline ini, staging menjadi tempat singgah agar SQL dapat membaca masukan sebagai tabel. Validasi tetap dilakukan di Python. Itulah sebabnya data tampak ditampung dua kali.

8. Apa yang terjadi jika gagal?

KondisiAkibat
Satu baris salahMasuk rejected; proses baris lain dilanjutkan.
Semua baris ditolakMode DB membuat staging kosong, melewati merge, lalu menulis laporan.
Header salah / file tidak ditemukanProgram berhenti sebelum laporan batch ditulis.
Kesalahan saat transaksi DBSemua perubahan DB pada batch dibatalkan; laporan batch belum ditulis.
Laporan gagal ditulis setelah commitData DB sudah tersimpan; laporan mungkin tidak lengkap.

Nama laporan memakai waktu lokal dan potongan UUID. CSV penolakan berisi nilai masukan, nomor baris, dan alasan. JSON memuat mode, path input, accepted, rejected, applied, skipped_same_or_older, dan path file penolakan.

updated_at berasal dari data CSV dan menentukan urutan pembaruan. Waktu pada nama laporan menunjukkan kapan pipeline dijalankan.
